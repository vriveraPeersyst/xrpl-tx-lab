summary: Caps an issuer's transfer fee (TransferRate) at a maximum of 100%, i.e. a value of 2000000000.
xrplDocs: https://xrpl.org/resources/known-amendments#fix1201

## What changes

Before this fix, the `TransferRate` field of an issuing account had no effective cap. `TransferRate` is expressed in billionths: `1000000000` means 0% fee and `2000000000` means 100%. An issuer could set values above `2000000000`, which was equivalent to charging more than 100% of the transferred amount on every payment of its tokens — something with no economic sense that broke assumptions of the payment engine.

With fix1201 active, [AccountSet](/tx/AccountSet) rejects with `temBAD_TRANSFER_RATE` any `TransferRate` greater than `2000000000`. The value `0` is still accepted as "no fee", and the valid range is between `1000000000` and `2000000000` inclusive.

## Affected transactions and objects

- [AccountSet](/tx/AccountSet): validation of the `TransferRate` field in `preflight`.
- [AccountRoot](/objects/AccountRoot): the stored `TransferRate` field can never exceed 100%.
- Indirectly, [Payment](/tx/Payment) and [OfferCreate](/tx/OfferCreate), which apply the fee when moving issued tokens.

## Status and context

This is one of the fixes numbered after its rippled GitHub issue (#1201). It was introduced in rippled 0.70.0 and has been active on mainnet and testnet for years. In the current code the amendment is retired (`XRPL_RETIRE_FIX(1201)` in `features.macro`): the corrected behavior is now the only one that exists, and there is no code branch "without the fix". It still appears in `server_definitions` and in the ledger's amendment list for historical compatibility.
