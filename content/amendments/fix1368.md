## What changes

For each step of a path, the payment engine calculates how much goes in and how much comes out. Issued token amounts use a 16-significant-digit decimal representation, and in certain combinations of conversions the arithmetic lost precision: the result of one step was rounded in a way that the next step "saw" less liquidity than actually existed. The consequence was that some perfectly well-funded payments failed with codes like `tecPATH_PARTIAL` or `tecPATH_DRY`.

fix1368 adjusts how the engine rounds and compares those intermediate amounts so that a payment that should complete actually does.

## Affected transactions and objects

- [Payment](/tx/Payment): especially cross-currency payments with `Paths` and `SendMax`.
- [OfferCreate](/tx/OfferCreate): offer crossing uses the same liquidity engine.
- [Offer](/objects/Offer) and [RippleState](/objects/RippleState) objects, whose balances are updated with the corrected amounts.

## Status and context

Numbered after rippled issue #1368. It was introduced in version 0.80.0 and activated on mainnet shortly after. Today it is retired in the code (`XRPL_RETIRE_FIX(1368)`), so the corrected behavior is the only one that exists. It's a typical example of the earliest protocol fixes: small changes that nonetheless alter transaction results and therefore require an amendment so that all validators apply them at the same time.
