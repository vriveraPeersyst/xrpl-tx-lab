## What changes

[PaymentChannelClaim](/tx/PaymentChannelClaim) lets a channel's recipient claim XRP by presenting a `Balance` and a signature from the sender. If the transaction was invalid (for example, a `Balance` lower than what was already claimed, or a signature that didn't verify), rippled in some cases returned a code that didn't describe the real cause, and in others a `tem` code where a `tec` was appropriate (or vice versa).

This matters because `tem` codes don't consume a fee or sequence (the transaction never enters the ledger), while `tec` codes do. Returning the wrong type changed the transaction's observable effect. fix1512 revises `PaymentChannelClaim`'s checks to return the appropriate code in each case.

## Affected transactions and objects

- [PaymentChannelClaim](/tx/PaymentChannelClaim): error codes from `preflight` and `preclaim`.
- [PayChannel](/objects/PayChannel): its structure doesn't change, only how claims against it are validated.

## Status and context

Numbered after rippled issue #1512. It was introduced in version 0.90.0 and is retired in the current code (`XRPL_RETIRE_FIX(1512)`). It's a good example of why even an "error codes only" change needs an amendment: if one validator returned `tem` and another `tec` for the same transaction, they would disagree on whether the fee is charged and the ledger would diverge.
