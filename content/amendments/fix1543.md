## What changes

Each transaction type defines which bits of the `Flags` field are valid; the rest are reserved and `preflight` must reject them with `temINVALID_FLAG`. Several transactors didn't perform that check, so they accepted transactions with garbage bits in `Flags`. That was a problem for the future: if a meaning was later assigned to one of those bits, old transactions with that bit set would retroactively change behavior.

fix1543 adds the flag-mask check to the types that had it incomplete, including [Escrow](/objects/Escrow) transactions ([EscrowCreate](/tx/EscrowCreate), [EscrowFinish](/tx/EscrowFinish), [EscrowCancel](/tx/EscrowCancel)), payment channel transactions ([PaymentChannelCreate](/tx/PaymentChannelCreate), [PaymentChannelFund](/tx/PaymentChannelFund)), and [SignerListSet](/tx/SignerListSet). Since then, any bit outside `tfUniversal` and the type's own flags triggers `temINVALID_FLAG`.

## Affected transactions and objects

The types listed above, in their `preflight` phase. It doesn't modify any ledger objects.

## Status and context

Numbered after rippled issue #1543. It was introduced in version 1.2.0 and is retired in the code (`XRPL_RETIRE_FIX(1543)`). The same idea was repeated years later with [fixInvalidTxFlags](/amendments/fixInvalidTxFlags) for `SignerListSet` and credential transactions, which were again born without a flag mask. Practical rule: on testnet, always send `Flags` with only the bits documented for the type.
