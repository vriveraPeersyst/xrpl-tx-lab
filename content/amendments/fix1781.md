## What changes

The payment engine rejects paths (`Paths`) that form a loop, i.e. that pass through the same account or order book twice, because they don't provide real liquidity and can be used to manipulate offers. The loop check didn't account for the path's endpoints when they were XRP: for example, an XRP → token → XRP payment could build a strand that started and ended at the same book without the engine detecting it.

fix1781 adds those checks: when building strands, the source and destination XRP steps are also considered for loop detection, and circular paths are discarded with `temBAD_PATH_LOOP`.

## Affected transactions and objects

- [Payment](/tx/Payment) with `Paths` involving XRP at both endpoints.
- Indirectly [Offer](/objects/Offer) and [RippleState](/objects/RippleState), which can no longer be traversed in a loop.

## Status and context

Numbered after rippled issue #1781. It was introduced in version 1.6.0 and is retired in the current code (`XRPL_RETIRE_FIX(1781)`). It's the last of the series of "numbered" fixes; from 2020 onward corrective amendments started carrying descriptive names (`fixCheckThreading`, `fixQualityUpperBound`, etc.).
