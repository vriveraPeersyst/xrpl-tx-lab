## What it does

`EnableAmendment` isn't sent by any account: it's generated by validators during consensus and appears in the ledger as if it came from the null account `rrrrrrrrrrrrrrrrrrrrrhoLvTp`, with no fee, no signature, and `Sequence: 0`. It's the mechanism by which the XRPL changes its own rules.

The voting process lives outside the transactor (in `AmendmentTable`), but the result is written to the ledger with this pseudo-transaction, always in a *flag ledger* (one of every `kFlagLedgerInterval` = 256 ledgers). It has three variants depending on the flags:

- `tfGotMajority` (65536): the amendment has just crossed the support threshold (`kAmendmentMajorityCalcThreshold`, 80% of trusted validators). It's recorded in `Majorities` of the [Amendments](/objects/Amendments) object along with the parent ledger's close time.
- `tfLostMajority` (131072): support has fallen below the threshold; it's removed from `Majorities`.
- No flags: the amendment has maintained majority for `kDefaultAmendmentMajorityTime` (2 weeks) and becomes permanently activated: it moves to the object's `Amendments` list and the new rules govern from the next ledger onward.

Once activated, an amendment can't be deactivated. And a server that doesn't know (doesn't "support") an activated amendment declares itself *amendment blocked* and stops processing transactions until it's updated.

## When to use it

You can't send it: any attempt to do so is rejected. It's worth understanding to:

- Track an amendment's status on testnet (`feature` RPC or the `Amendments` object) and know when new rules will take effect.
- Interpret the history of a flag ledger when transactions appear with no issuing account.
- Understand why a node becomes *amendment blocked* after an activation.

## How it works inside

The three pseudo-transactions (`EnableAmendment`, [SetFee](/tx/SetFee), [UNLModify](/tx/UNLModify)) share the `Change` transactor (`src/libxrpl/tx/transactors/system/Change.cpp`).

`Transactor::invokePreflight<Change>` requires that `Account` be the zero account (`temBAD_SRC_ACCOUNT`), that `Fee` be exactly 0 XRP (`temBAD_FEE`), that there be no `SigningPubKey`, `TxnSignature`, or `Signers` (`temBAD_SIGNATURE`), and that `Sequence` be 0 with no `PreviousTxnID` present (`temBAD_SEQUENCE`). With [LendingProtocol](/amendments/LendingProtocol) active, it also validates the flags against `tfEnableAmendmentMask`.

`Change::preclaim` rejects with `temINVALID` any attempt to apply it against the open ledger: it can only enter as part of consensus close. It's the barrier that prevents a user from injecting it. For `ttAMENDMENT` there are no further checks.

`Change::doApply` dispatches to `Change::applyAmendment`:

1. Reads (or creates, if it doesn't exist) the `Amendments` object. If the hash is already in the active list, `tefALREADY`.
2. If it carries both `tfGotMajority` and `tfLostMajority` at once, `temINVALID_FLAG`.
3. Rebuilds the `Majorities` array without this amendment's entry. If it came with `tfGotMajority` and was already present, `tefALREADY`; if it came with `tfLostMajority` and wasn't present, also `tefALREADY`.
4. With `tfGotMajority`, adds a `Majority` entry with `Amendment` and `CloseTime` (parent ledger's close time). With no flags, adds the hash to `Amendments`, notifies `AmendmentTable::enable`, and, if the server doesn't support that amendment, calls `setAmendmentBlocked`.
5. Saves the object (removes `Majorities` if it ends up empty).

The computation of the 80% and the two weeks doesn't happen here: each validator does it when voting at the flag ledger, and `fixAmendmentMajorityCalc` (already integrated into the code) corrected the calculation so it's "more than 80%" of the UNL validators.

## Key fields

- **Amendment** — 256-bit hash identifying the amendment (the same `id` you see in `feature` or in testnet.json).
- **LedgerSequence** — index of the flag ledger in which it's applied.
- **Flags** — `tfGotMajority`, `tfLostMajority`, or none (activation).

## Flags

- **tfGotMajority** (65536) — the amendment has reached majority; starts the two-week countdown.
- **tfLostMajority** (131072) — it has lost majority; it's removed from `Majorities` and the countdown resets if it regains it.

## Common errors

These codes only appear in a validator's logs; the user never sees them.

- **temBAD_SRC_ACCOUNT / temBAD_FEE / temBAD_SIGNATURE / temBAD_SEQUENCE** — someone tried to send a pseudo-transaction from a real account, with a fee, signed, or with a sequence.
- **temINVALID** — the pseudo-transaction reached the open ledger instead of consensus close.
- **tefALREADY** — the amendment was already activated, already had majority, or had already lost it.
- **temINVALID_FLAG** — `tfGotMajority` and `tfLostMajority` at once.

## Example

This is how an activation appears in the ledger (no flags):

```json
{
  "TransactionType": "EnableAmendment",
  "Account": "rrrrrrrrrrrrrrrrrrrrrhoLvTp",
  "Amendment": "9F287AED3CDB50A7BD1ACEC24296A30C9B5230CCD136219317AC790E3B884377",
  "LedgerSequence": 20800000,
  "Fee": "0",
  "Sequence": 0,
  "SigningPubKey": ""
}
```

It can't be sent: the system constructs it. To observe it, look for a flag ledger (a multiple of 256) with `ledger` and `transactions: true` at a time when an amendment changes state, or query the [Amendments](/objects/Amendments) object with `ledger_entry` (`amendments: true`).
